
# 方案选型：索引优先，而不是把东西搬整齐

**日期**：2026-11-04　**状态**：confirmed

## 背景

四层架构跑通后发现真实问题不是"引擎不能跑"，而是**跑完找不回来**：

- 12G 老 SD1.5 库（当时在 `WIN11/热数据/sd-webui-models`）不在项目树内，名字上也看不出它属于哪个项目
- 产物散在三处：HDD 主池顶层 11M 平铺 PNG、A1111 自己的 `outputs/`、ComfyUI 的 `output/`
- 三个 0 字节占位目录 + 两个废弃 venv（322M）+ 一份重复权重副本（255M）
- 每个启动脚本各自硬编码绝对路径，改盘要改 N 处

初版方案（v1）的判断是：把这 12G 权重搬进项目树，让物理位置和逻辑归属一致。

## 方案 A：物理整理（v1 思路）

结论：**否决**。

搬 12G 跨卷 `mv` 要真拷数据（HDD→SSD），耗时且中断会留下半成品。更重要的是，搬完之后路径仍然分散——只是分得更"整齐"了一点。**乱源不是位置散，是没有索引**。

补充发现：跨卷移动会同时打断 A1111 的 `models` 软链、ComfyUI 的 `extra_model_paths.yaml`，两处引用一起改，风险高于收益。

## 方案 B：索引优先（v2，采纳）

结论：**采纳**。

核心判据：**同卷内 `mv` 是 O(1) 改名，跨卷才是真拷贝**。所以只在同卷内做重命名，跨卷一律用软链。

三条落地：

1. **HDD 侧为唯一逻辑根**，根下放两样东西：
   - `MAP.md`：一屏索引，回答"由什么组成、实体在哪、怎么启动"
   - `PATHS.env`：绝对路径唯一真相源，脚本 `source` 它
2. **`apps/` 与 `models/` 两层软链**（共 16 个），把 WIN11 侧的 3 个引擎和 13 个权重库"搬到眼前"，实体一个字节都不动
3. **权重仓同卷改名**：`WIN11/热数据/sd-webui-models` → `WIN11/ai-image-lab/models/legacy-sd15`（O(1) 改名），只改 2 处引用（A1111 的 `models` 软链、ComfyUI 的 `extra_model_paths.yaml`）

**为什么软链不是冗余**：初看"多一层跳转"确实像无用中间层。但它的语义是**索引的物理化**——让 `find` 之外的人类打开项目根就能看见全貌。前提是软链只出现在 `apps/`、`models/` 两层入口，**不往深处套第二层**（深层再套会让 `find`、`rsync`、备份全部变味）。

## 决策

采纳方案 B。执行分四档，逐档验收：

| 档 | 内容 | 结果 |
|---|---|---|
| A | MAP.md / PATHS.env / README 各就位 / 删 4 个 0B 空壳 | 完成 |
| B | 补 chilloutmix 缺失权重（运行副本缺 267M）/ 落地单向 `sync-models.sh` | 完成，两侧 32 文件对齐，md5 一致 |
| C | 权重同卷改名 + 改 2 处引用 + 产物三处归一到 `outputs/` | 完成，30 文件，旧路径已清空 |
| D | 清 venv.broken-*(322M) / broken-checkpoint(255M) | 完成，释放约 577M，目录保留 |

验收方式：`check-paths.sh` 全绿（0 处悬空）、`sync-models.sh --check` 退出码 0、产物顶层无残留。

## 约束与风险

- **A1111 不能动**：目录名与位置被 `webui-user.sh` 的 `install_dir`+`clone_dir` 拼接依赖；`venv` 内 41 个文件含绝对路径。它永远留在 HDD，只靠软链进入索引。
- **`_sdwebui-backup/` 目录不能整删**：双击 `.app` 启动器的 `launch` 脚本把它当日志目录写 `run.log`。只删了里面的重复权重，目录本身保留。
- **跨卷硬约束仍在**：权重在 SSD、产物在 HDD 的分工不变。索引只解决"找得到"，不解决"搬得快"。
