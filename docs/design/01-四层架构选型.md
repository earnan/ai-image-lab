
# 方案选型：四层并存，且引擎可以留在机械盘

**日期**：2026-11-04　**状态**：confirmed

## 背景

M2 Mac mini，统一内存 16GB，外置 SSD（APFS，实测 ~328MB/s）与机械盘 HDD（~92MB/s）。需要在本地完成从快速出图到精细控制的全谱任务。

有两个候选路线：

- **方案 A：单引擎通吃** —— 只装 ComfyUI，靠节点覆盖所有场景
- **方案 B：四层并存** —— Draw Things / ComfyUI / webui / 云端各司其职

以及一个资源分配问题：引擎（程序本体，几个 GB 的小文件）和权重（3–8GB 大文件）该分别放哪块盘。

## 方案 A：单引擎通吃

结论：**不可用**。

三个硬性不兼容：
1. **模型格式不通用**。Draw Things 用自家 `.ckpt` 打包格式（`drawthings/` 7.3G 不可拆），ComfyUI 用分离式 `diffusion_models` + `text_encoders` + `vae`。同一套权重无法两边共用。
2. **16GB 跑不动全量 Flux**。必须走 GGUF 量化，而量化生态在 ComfyUI 侧成熟、在 Draw Things 侧走另一套打包逻辑。
3. **老 SD1.5 库（12G）只能在 webui 上跑**。chilloutmix 这类模型依赖 webui 的旧式加载链，换引擎等于放弃这批存量资产。

放弃的代价是：留着四套引擎，就要维护四套路径、四套产物落点。

## 方案 B：四层并存

结论：**可用，且是唯一可行解**。

| 层 | 引擎 | 实测耗时 | 不可替代的理由 |
|---|---|---|---|
| L1 | Draw Things CLI | 33s（含模型加载） | 苹果原生 Metal，日常快速出图最快 |
| L2 | ComfyUI + GGUF | 54s | 节点流 + ControlNet；量化让 16GB 能跑 Flux |
| L3 | webui | ~30s | 唯一能跑存量 SD1.5 库 |
| L4 | 云端 API | 10–30s | 突破本机算力上限的 4K 复杂构图 |

四层的真正代价不是磁盘，是**产物会散落四处**——这个问题在 [design/02](02-索引优先整理方案.md) 解决。

## 决策：引擎放哪块盘

**权重必须放 SSD，引擎可以放 HDD。**

依据是读写频次，不是体积：

| 对象 | 读取模式 | 放 SSD 的收益 |
|---|---|---|
| **权重**（3–8GB） | 每张图都可能重读 | **决定性**。实测 GGUF 2.3GB 从 HDD 加载 25s+，从 SSD 约 3s。放慢盘不是"稍微慢点"，是把 33s 的出图变成近 60s |
| **引擎**（约 500MB 小文件） | 启动时读一次 | 边际。启动那一次多等几秒，之后整个会话不再读 |

所以早期把引擎也迁到 SSD、把权重挤到 HDD 的排布是**反的**——权重才是热数据。

**约束与风险**：
- 引擎在 HDD 意味着每次冷启动多几秒。若将来出现"每次出图都重新加载引擎"的场景（例如频繁启停的自动化批处理），这个前提失效，需重新评估。
- 权重全压在单块外置 SSD 上：该卷故障时无在线副本，legacy-sd15 可从 `<HDD卷>/work/data/models/sd-webui` 恢复，其余需重下。
